# BlueSight v1.2 — Proxy Health (design)

**Date:** 2026-07-25
**Status:** Validated brainstorm, pre-implementation
**Target version:** 0.2.0

## Goal

Make BlueSight surface the health of the ESPHome Bluetooth **proxies themselves**
— not just the GATT slot layer — so a proxy that goes offline, stalls (online
but no longer scanning), or reboots in a loop becomes a visible, actionable
incident instead of an invisible cause of "my Bluetooth is flaky".

## Grounding finding (probed on the user's live HA, 2026-07-25)

The real ESPHome proxy nodes (AtomeSalon/Parents/Buanderie/Valentine) run
**minimal bluetooth-proxy configs**: they expose only `update`, `light`,
`button`, a physical-button `binary_sensor`, and router-side `device_tracker`.
There are **no** `uptime`, `wifi_signal`, or `free_heap`/RAM sensors. So the
original "aggregate ESPHome diagnostic sensors" premise does not hold for the
common case.

**Better source, already in BlueSight's stack:** the `habluetooth` **scanner
registry** — the same library BlueSight rides for slot allocations. Confirmed
API (habluetooth on HA 2026.7):

```python
# manager
async_register_scanner_registration_callback(callback, source) -> CALLBACK_TYPE
    # callback gets HaScannerRegistration(event, scanner)
async_current_scanners() -> list[BaseHaScanner]

# models
class HaScannerRegistrationEvent(Enum): ADDED / REMOVED / UPDATED

# BaseHaScanner
.source            # adapter MAC
.name              # friendly scanner name (e.g. "atomesalon")
.connectable       # bool
time_since_last_detection() -> float   # seconds since last advertisement seen
discovered_devices -> list[BLEDevice]  # devices currently seen
# habluetooth's own SCANNER_WATCHDOG_TIMEOUT drives its internal watchdog
```

This is **zero user config**, authoritative for the BLE role, and consistent
with BlueSight's "ride habluetooth" philosophy. RAM/WiFi telemetry is
deliberately deferred to the v1.5 ESPHome component, where it belongs.

## Design (reuses the v1 architecture)

### Pure model
```python
@dataclass(frozen=True, slots=True)
class ProxyHealth:
    source: str                     # proxy adapter MAC
    name: str
    connectable: bool
    online: bool                    # present in async_current_scanners()
    seconds_since_detection: float  # time_since_last_detection()
    device_count: int               # len(discovered_devices)
```

### Three new pure detectors (HA-free, unit-tested)
- **`PROXY_OFFLINE`** — a source in the session's *known* set is absent from the
  current online scanners → offline incident.
- **`PROXY_STALLED`** — `online and seconds_since_detection > threshold`
  (default ~180 s, above habluetooth's own watchdog so we don't race its
  recovery). The "zombie" case: registered but no longer scanning.
- **`PROXY_REBOOT_STORM`** — N REMOVED→ADDED cycles within window T, via the
  existing `FailureWindow` (record on each REMOVED).

New `IncidentKind` members: `PROXY_OFFLINE`, `PROXY_STALLED`,
`PROXY_REBOOT_STORM`. Incident `address` field carries the proxy source; `sources`
carries `[source]`.

### Thin HA shell
- **`ScannerAdapter`** (twin of `SlotAdapter`): subscribes to
  `async_register_scanner_registration_callback`; on REMOVED, records into a
  reboot `FailureWindow`; triggers a coordinator refresh on any event.
- **`current_proxy_health(manager)`** (in `adapter.py`): maps
  `async_current_scanners()` → `list[ProxyHealth]`.
- **Coordinator**: `_snapshot` also builds proxy health; `BleTriageData` gains
  `proxies_health: list[ProxyHealth]`; the proxy incidents are appended to the
  **same** `incidents` list. The global `binary_sensor.bluesight_incident`,
  notifications (with precedence), and dashboard pick them up for free.
- **Known-sources**: in-memory per HA session. A source becomes "known" the
  first time it is seen online; if it later disappears from current scanners →
  offline. Resets on HA restart (we only flag what we have seen alive — no
  invented cross-restart persistence).

### Entities (per proxy, minimal — YAGNI)
- `binary_sensor.<proxy>_online` (device_class connectivity)
- `sensor.<proxy>_last_device_seen` (seconds since last detection, or a
  timestamp)
- optional `sensor.<proxy>_devices_seen` (count) — include if cheap/useful

### Notifications
Proxy incidents flow through the existing `NotificationManager` + precedence.
Add actionable messages per kind (offline → check power/WiFi; stalled →
power-cycle; reboot-storm → check power supply/brownout).

### Config
Options flow gains: stalled threshold (s), reboot-storm count + window (s).
Version bump to **0.2.0**.

## Testing
- Pure detectors + `ProxyHealth` model: full unit tests (Windows).
- `ScannerAdapter` + `current_proxy_health`: fake-manager tests (Windows),
  same pattern as `SlotAdapter`.
- Coordinator health snapshot: fake-manager + reboot-window tests (Windows);
  full HA-fixture wiring runs on CI/Linux.

## Out of scope (v1.2)
- RAM/WiFi/uptime telemetry (→ v1.5 ESPHome component).
- Any *action* (restart a proxy) (→ v2 self-healing).
- Cross-restart known-source persistence.

## Roadmap context
v1.2 proxy health (this) → v1.3 generalized dead-bond detection (the killer;
uses proxy health to tell "proxy dead" from "bond dead") → v1.4 connection
quality / best-proxy advisor → v1.5 ESPHome component (the moat: raw
SMP/RAM/bond telemetry).
