# BlueSight v1.5 — ESPHome telemetry component (design)

**Date:** 2026-08-24
**Status:** Validated brainstorm, pre-implementation
**Target version:** 0.5.0 (0.4.0 ships the embedded Lovelace card first)

## Goal

Give BlueSight evidence it cannot get from Home Assistant: real SMP pairing
failures, the proxy's NVS bond list, and per-connection idle time. This turns
storm detection from a heuristic into a measurement, and lifts the documented
ghost-slot limitation for BLE devices Home Assistant does not manage.

## Grounding findings (probed 2026-08-24)

Two facts overturn the roadmap entry as written in the README.

**1. There is no NimBLE.** The README promises "NimBLE SMP-fail counts".
ESPHome 2026.2.4's `esp32_ble` contains zero NimBLE references — it is
Bluedroid only. The user's own proxy configs already document this: the
`CONFIG_BLE_SM_*` options are NimBLE symbols Bluedroid never reads. Every
counter below therefore comes from the Bluedroid GAP/GATTC event stream.

**2. The SMP evidence already crosses the wire, and dies in an `except`.**
`bluetooth_proxy/bluetooth_connection.cpp:483` handles
`ESP_GAP_BLE_AUTH_CMPL_EVT` and already calls
`send_device_pairing(address, false, param->ble_security.auth_cmpl.fail_reason)`
over the native API. `send_device_connection(..., param->disconnect.reason)`
does the same for GATT disconnect reasons. But `habluetooth` 6.1.0 exposes no
`disconnect_reason` / `fail_reason` / pairing surface at all: these reasons
surface in `bleak-esphome` as `BleakError`s raised to whichever integration
owns the connection. They are visible in logs, unobservable by a third party.

So the data exists, travels, and is thrown away. A firmware-side observer is
the only way to keep it.

**3. ESPHome fans BLE events out to every registered handler.**
`esp32_ble/ble.h:129,137` expose `register_gap_event_handler()` and
`register_gattc_event_handler()` publicly, and `ble.cpp:398,456` dispatch each
event to all registered handlers. A component can therefore observe exactly the
events `bluetooth_proxy` sees without touching its connections — BlueSight's
read-only invariant holds all the way into the firmware.

## Design

### Firmware: `esphome/components/bluesight/`

A passive observer registered as `GAPEventHandler` + `GATTcEventHandler`. It
opens no connection, writes no bond, and never calls into `bluetooth_proxy`.

Three text sensors per proxy. All three carry **facts, never verdicts**: the
ESPHome ecosystem norm is that firmware publishes measurements and the Home
Assistant side decides policy. Putting a threshold in the firmware would bury
detection logic in a binary that pytest cannot reach and that cannot be
retuned without a reflash — the opposite of the invariant the rest of BlueSight
is built on.

| Entity (`original_name`) | Payload | Source | Bound |
| --- | --- | --- | --- |
| `bluesight_smp_failures` | `MAC:count` pairs | `ESP_GAP_BLE_AUTH_CMPL_EVT`, `success == false`, keyed by `bd_addr` | ≤ 8 addresses × 15 = 120 |
| `bluesight_bonds` | `MAC` list | `esp_ble_get_bond_device_list()` | ≤ 15 bonds × 13 = 195 |
| `bluesight_slots` | `MAC:idle_secs` pairs | GATTC connect/disconnect + last-traffic timestamp | ≤ 9 slots × 17 = 153 |

MACs are compact 12-character hex without separators. Every payload stays under
Home Assistant's 255-character state limit **by construction**, not by
truncation: the hardware caps (Bluedroid's bond store, `max_connections`) sit
below the string cap. Verify both at implementation time.

Counts are monotonic since boot. The component owns these sensor names in
codegen — the user never writes them in YAML — which is what makes
`original_name` a stable discovery key.

### Distribution

`esphome/components/bluesight/` lives in this repo, pulled with:

```yaml
external_components:
  - source: github://dasimon135/ha-bluesight@v0.5.0
    components: [bluesight]
```

One release, one version, so the firmware↔integration data contract cannot
drift. HACS ignores the `esphome/` directory.

### Home Assistant: discovery and reading

BlueSight starts from the `source` (adapter MAC) habluetooth already gives it,
resolves the ESPHome device through the MAC→device index it already builds
(`coordinator.py:289-319`), then walks that device's entities in the entity
registry.

**Match on `original_name`, not `unique_id` and not `entity_id`.** An
`entity_id` is user-renameable. An ESPHome `unique_id` is an implementation
detail of another integration — coupling to its format is exactly what
BlueSight's architecture exists to avoid. `original_name` keeps the name the
integration supplied and survives user renames, and our component owns it.

Reading is confined to one isolated reader module, on the `adapter.py` model:
one file to touch if the entity surface ever moves.

### Pure model: `telemetry.py`

```python
ProxyTelemetry(source, smp_failures, bonds, slot_idle_seconds)
```

No Home Assistant dependency; unit-tested with plain pytest. Parses the three
raw states into typed structure.

**Absent, `unavailable` or `unknown` yields `None`, never zero.** The
distinction carries weight: a rebooting proxy drops its ESPHome entities to
`unavailable`, and reporting zero SMP failures at exactly the moment a proxy is
in trouble would be a lie.

**A counter that decreases means a reboot, not a recovery.** BlueSight windows
deltas; any decrease rearms the baseline without counting a failure.

## Detection

### STORM — upgraded in place, per proxy

`Incident` gains an `evidence` field (`"smp"` | `"heuristic"`). It is
**deliberately excluded from `Incident.key`**: the same incident is the same
incident however it was observed, and including it would make a proxy that
switches modes emit a duplicate.

Per proxy, if telemetry is present the per-address SMP delta feeds the existing
`FailureWindow` in place of `ReleaseTracker`; otherwise the heuristic stands. A
mixed fleet degrades proxy by proxy, and the attribute says which signal spoke.

### BOND_LOST — new

An address accumulating SMP failures on a proxy **and** absent from that proxy's
bond list: pairing is being attempted, it is failing, and no bond exists. The
remedy is exact — re-pair via *this* proxy. More specific than STORM, so it
takes precedence in `incident_policy`.

### GHOST_SLOT — extended to unmanaged devices

`idle_secs` past threshold on an address absent from the device registry: the
case `is_device_alive()` conservatively calls alive today
(`availability.py:24`). For HA-managed devices the existing entity-based
verdict still wins — it is the more semantic signal. Closes the limitation
documented at README:231.

## Configuration

Three new options-flow settings: slot idle threshold, SMP window, bond
threshold. All live on the Home Assistant side, so retuning never requires a
reflash.

## Testing

- `telemetry.py`, both new detectors, and the counter-reset logic: pure pytest
  on Windows, like every other detector.
- The isolated reader: fake-registry tests, same pattern as `test_adapter.py`.
- The firmware is not testable in CI. That constraint drove the whole design:
  it holds no threshold, no judgement, and nothing that should be tunable
  without a reflash.

## Out of scope (v1.5)

- BLE RAM / free-heap telemetry and `ESP_GATT_NO_RESOURCES` reject counters.
- Aggregated GATT disconnect-reason histograms.
- Any remediation action (→ v2 self-healing).
